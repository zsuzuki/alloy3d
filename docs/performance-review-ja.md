# 基礎性能・バッファ管理レビュー

2026-09-09。比較元は `8c55006`。公開C++ APIの呼び出し方を維持し、
固定容量の撤廃とCPU側の重複処理の削減を行った。

## 発見した問題と修正

| 優先度 | 問題 | 修正 |
| --- | --- | --- |
| 高 | 2D/3Dの線・面・文字・スプライト用バッファが固定長で、書き込み時の容量チェックがない | 共通の `VertexBuffer<T>` で必要時に拡張。既存データを保持し、整数オーバーフローとMetalデバイスの上限を検査 |
| 高 | 2DのUniformsだけが1個で、GPUが前フレームを処理中でもCPUが画面サイズを上書きする | 頂点バッファと同じ3ページに分離 |
| 高 | drawable取得失敗時にもUpdateが描画要求を追加し、消費されず蓄積する | そのフレームの一時描画要求を破棄。GPUに送らなかったページは進めない |
| 中 | 球が三角形ごとにロック・Objective-Cメッセージ送信・色変換する | 球全体を一度に予約し、1回のロック内で直接頂点を生成 |
| 中 | 同じモデルを繰り返し描くと、同じ関節行列を毎回コピー・同期する | ページごとに更新の有無を管理。姿勢更新後の最初の利用だけ転送 |
| 中 | モデルの描画要求ごとにshared_ptrとlistノードを確保・解放する | 所有権を保持する移動可能な要素をvectorに格納し、容量を再利用 |
| 中 | モデル読み込み後にもCPU側の元頂点・インデックスを重複保持する | GPUバッファ作成後に使わないコピーを撤廃 |
| 中 | 文字キャッシュのヒット時にも毎回フォント・色の文字列整形を実行する | フォント設定部分のキーを保持し、フォント・サイズ・色の変更時だけ更新 |
| 中 | 短い排他区間にdispatch semaphoreを使う | `os_unfair_lock` に変更。バッファ拡張中のポインタ無効化を防ぐため、予約から書き込み完了までRAIIで保護 |
| 中 | SharedバッファにManaged用の `didModifyRange:` を呼んでいる | Sharedバッファの不要な通知を撤廃。Apple Silicon専用のモデルバッファもSharedに統一 |
| 低 | シェーダー関数、Depth設定、Rendererのキュー等に解放漏れがある | 所有権に合わせて解放。Renderer破棄前はGPU完了を待つ。借用したCGColorSpaceの過剰解放も修正 |

## メモリの扱い

以前は一時頂点バッファだけで **75,840,000 bytes（約72.33 MiB）** を
初期化時に予約していた。これは構造体サイズと確保数から計算したバッファの
合計サイズであり、プロセスの実測RSSではない。

現在は未使用の頂点バッファを確保しない。各用途・各ページについて、初回は
最低256頂点、以後は必要量まで原則2倍に拡張する。現在フレームで書き込んだ範囲
だけをコピーし、確保済み容量内のフレームでは再確保しない。
3ページはGPU処理中のデータを保護するためのもので、頂点数の固定上限ではない。

ピーク容量は再利用のため保持し、自動縮小は行わない。一時的に大きなシーンを
描くと、その後も容量を保持する。後続の改善で、シーン切替時の明示解放と
文字キャッシュ予算の[公開API](render-memory-ja.md)を追加した。事前予約は未追加。
初回と拡張時には確保・コピーのコストがあり、このコストは下記の定常計測には
含まれない。

デバイス上限を超える要求は `std::length_error`、Metalの確保失敗は
`std::bad_alloc` で通知する。バッファ拡張に失敗しても元のバッファとデータを
保持し、描画要求数を増やさない。例外を無視して描画を欠落させる方式ではない。

描画・モデル更新はApplicationLoopのコールバックから行う。
コンテキスト全体やモデルの並行変更、描画要求追加とrenderの同時実行は未対応。

## 実測

Apple M3 Ultra、Release / AppleClang 21、256×256オフスクリーン描画。
同じ検証プログラムを修正前後のライブラリにリンクして比較した。
各ケース80フレームのうち先頭10フレームを除き、70フレームの中央値を記載。
Metal検証レイヤーとSanitizerを無効にした性能測定と、有効にした回帰検証を分けた。

| ケース | 測定区間 | 修正前 ms | 修正後 ms |
| --- | --- | ---: | ---: |
| 2D/3D線各10,000本＋2D矩形1,000個 | CPU描画要求生成 | 0.2310 | 0.2148 |
| 球100個（24×12分割） | CPU描画要求生成 | 0.6703 | 0.2177 |
| 同じモデル1,000個 | CPU描画要求生成 | 0.0326 | 0.0091 |
| 同じモデル1,000個 | CPU描画命令登録 | 0.2082 | 0.1734 |
| 同じ文字列を2D/3D各100回 | CPU描画要求生成 | 0.8493 | 0.0689 |

球の要求生成は約68%、文字の要求生成は約92%短縮した。
線の差は小さく、実行間の変動もあるため大きな高速化とは評価しない。
GPU時間は線ケース1.1198→1.1195ms、球0.0764→0.0721ms、
モデル0.0199→0.0199ms、文字0.0147→0.0144msで、ほぼ同水準。

これは限定した負荷でのCPUホットパスの比較であり、アプリ全体のFPS改善率ではない。
各フレームでGPU完了を待つため、通常の3フレーム並列動作のスループット測定でもない。
文字はキャッシュ済み、モデルは小さい付属アセット、線やモデルは同じ場所に重ねている。
GPU時間から一般的なシーンの描画性能を推定することはできない。

## 検証と再現手順

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DALLOY3D_BUILD_TESTS=ON
cmake --build build -j 8
ctest --test-dir build --output-on-failure

build/tests/alloy3d_render_probe build/shaders/shaders.metallib \
  "$PWD/assets/samples/models/animated_bouncer.glb"
build/tests/alloy3d_render_probe build/shaders/shaders.metallib \
  "$PWD/assets/samples/models/animated_bouncer.glb" --snapshot
```

- Releaseビルドでライブラリ・サンプルビューア・テストのビルド成功。
- ReleaseとDebug＋AddressSanitizerの両方で、Metal検証レイヤーを有効にした
  CTest 2件が成功。CPUの範囲外アクセス・use-after-freeの検出も併用した。
- `render_stress`: 線各65,000本、2D矩形21,000個、球180個（311,040頂点）、
  2D/3D文字各5,100件をそれぞれ6フレーム描画。以前の全種類の一時バッファ上限を
  超え、3ページを2巡する条件をMetal検証レイヤーで検証。
- `buffer_regression`: 350,000要素への拡張とデータ保持、容量再利用、整数上限の拒否、
  確保失敗時のデータ保持、フォント設定変更によるキャッシュ無効化、アニメーション
  更新の全ページ反映を確認。
- 同テストでは画面サイズが異なる3フレームを全てencodeしてからGPUへ送信。
  各画像の矩形幅が正しいことをピクセルで確認し、破棄フレームとページ再利用も検証。
- 球・モデル・2D/3D文字を含む固定シーンの修正前後のピクセルハッシュが一致：
  `93ecf6623517c551`、非黒ピクセル数15,429。同一マシン・同一条件での比較であり、
  OSやフォントが異なる環境の固定期待値にはしていない。

Metal GPUを利用できない環境ではテストは終了コード77でskipする。
今回のGPUテストは実機で実行し、skipではなく成功を確認した。
ウィンドウの最小化などOSイベントを伴うGUI操作は自動検証していない。

## 次の改善候補

今回の小さな変更では、描画順やシェーダーの仕様を変える機能は追加していない。
次の項目はコード上の候補であり、今回の計測で重大なボトルネックと断定したものではない。

1. **アニメーション姿勢の一時領域**：毎更新でNodeDataの名前・子配列までコピーし、
   ローカル行列・ワールド行列・訪問フラグを確保する。多数のリグではTRS専用配列と
   作業領域の再利用を先に計測する。
   → 対応済み：[アニメーション更新の改善結果](animation-performance-ja.md)。
2. **多数の同一モデル**：今回は要求管理と関節転送を削減したが、draw callは個数分残る。
   実際に命令登録が支配的なシーンなら、明示的なインスタンス描画APIを検討する。
3. **文字キャッシュのメモリ予算**：CPU画像とGPUテクスチャの両方を最大512件保持する。
   件数制限はバイト数の制限にならず、長い文字列では重い。使用バイト量に基づく上限が候補。
   → 対応済み：CPU/GPU別のバイト予算とLRUを追加。
4. **ピーク後のバッファ解放**：シーン切替時など、GPU完了後に明示的に縮小・解放できる
   APIなら、毎フレームの再確保を増やさずメモリを返却できる。
   → 対応済み：[文字キャッシュ予算と描画メモリの解放](render-memory-ja.md)。
5. **GPU側の描画量**：カリングやインスタンシングの前に、実利用シーンの解像度・
   透明描画・重ね描きとCPU/GPU時間を採取する。今回の結果だけではGPUの余裕は保証しない。
